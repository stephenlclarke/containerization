# Pull request 70: serialize VM-backed cctl NBD integration coverage

## Change

Pull request
[#70](https://github.com/stephenlclarke/containerization/pull/70) routes every
VM-backed `cctl --block` case through the integration suite's existing
exclusive Virtualization.framework lane. The malformed-spec check remains
concurrent because it fails validation before booting a VM.

## Motivation and context

Apple pull request
[#903](https://github.com/apple/containerization/pull/903) introduced the
coverage. Fork issue
[#65](https://github.com/stephenlclarke/containerization/issues/65) and pull
request [#66](https://github.com/stephenlclarke/containerization/pull/66)
established the same VZ scheduling boundary for the two-VM persistence case.

The 0.14.1 release gate subsequently showed the mount and raw cases completing
their guest commands before Virtualization.framework stopped their VMs during
concurrent teardown. The already-exclusive persistence case passed immediately
afterward.

Related issue:
[#69](https://github.com/stephenlclarke/containerization/issues/69).

## Validation

- Before the change, the release gate passed 181/185 cases, skipped two, and
  failed only the mount and raw cases with `VZErrorDomain Code=1`.
- After the change, the filtered `cctl block` group passes 4/4 with default
  concurrency in 6.73 seconds.
- The output proves the validation-only case runs in the concurrent lane,
  followed by all three VM-backed cases sequentially in the exclusive lane.
- Swift formatting, license checks, Markdown lint, and diff checks pass.

## Compatibility and risk

Production behavior and the NBD assertions are unchanged. The only trade-off
is several seconds of intentional serialization in the integration suite,
removing a host-level VZ scheduling failure from release validation.

## Upstream handoff

After exact-head review and required checks, the same minimal scheduling
correction and before/after evidence can be offered to Apple against the
originating pull request.
